# TanStack Query — Pagination, `keepPreviousData` & Infinite Scroll

## 1. Three Ways to Page Through the Same Data

All three files solve the identical problem — paging through `dummyjson.com/products` — using progressively more of what TanStack Query offers. Reading them side by side is really a story of **what problem each next tool solves**:

| | `App.jsx` | `TanStack.jsx` | `Infinite.jsx` |
|---|---|---|---|
| **Fetching** | Manual `axios` + `useEffect` | `useQuery` | `useInfiniteQuery` |
| **Pagination style** | Page N replaces page N-1 | Page N replaces page N-1 | Page N **appends** to page N-1 |
| **UI pattern** | Prev / Next buttons | Prev / Next buttons | "Load more" button |
| **Caching between pages** | None — refetches every click | Automatic, per `page` in the key | Automatic, one growing cache entry |
| **Loading flicker on page change** | Yes — `products` briefly `null` | No — old data stays visible, dimmed | N/A — new page just appends |

`main.jsx` currently renders `<Infinite />` — the other two are earlier stages of the same exercise, kept around as reference rather than deleted.

## 2. `App.jsx` — Pagination by Hand

```jsx
const [products, setProducts] = useState(null);
const [page, setPage] = useState(0);

const getAllProducts = async () => {
  let res = await axios.get(`.../products?limit=${limit}&skip=${page * limit}`);
  setProducts(res.data);
};

useEffect(() => { getAllProducts(); }, [page]);
```

- `skip=${page * limit}` — this is the actual pagination math: page 0 skips 0 items, page 1 skips `limit` items, page 2 skips `2 × limit`, and so on. Every "page" is really just a different `skip` offset into the same flat list.
- `useEffect(..., [page])` — refetches **every time `page` changes**, not just once on mount (the dependency array is the whole mechanism here).
- **The gap this leaves:** `products` is `null` while a new page loads, so — unless you reason carefully about when `null` shows up — clicking "Next" flashes the grid empty for a beat before the new page's data lands. There's also no cache: clicking `Next` then `Prev` back to a page you've already seen re-fetches it from scratch rather than reusing what you already downloaded.

```jsx
let totalPages = Math.ceil(products?.total / limit);
```

`products?.total` is `undefined` on the very first render (before any fetch resolves), and `Math.ceil(undefined / limit)` evaluates to `NaN` — harmless here since it only briefly shows "page 1 of NaN" before the first fetch resolves, but worth recognizing as the shape of the gap: optional chaining stops the **crash**, but doesn't stop a garbage value from existing for a render or two.

## 3. `TanStack.jsx` — Same UI, `useQuery` + `keepPreviousData`

```jsx
let { data, isPending, isError, isPlaceholderData } = useQuery({
  queryKey: ["products", page],
  queryFn: () => getAllProducts(limit, page),
  placeholderData: keepPreviousData,
});
```

### 3.1 The Key Difference: `placeholderData: keepPreviousData`

This single option is what solves `App.jsx`'s flicker problem. Without it, changing `page` (part of the `queryKey`) means TanStack Query treats page 1 and page 2 as **completely separate cache entries** — switching to a "new" key normally drops back to a loading state while that key's data is fetched fresh. `keepPreviousData` overrides that: while the new page is loading, the **previous page's data stays rendered** instead of disappearing.

### 3.2 `isPlaceholderData` — Telling the User What They're Looking At

```jsx
<div style={{ opacity: isPlaceholderData ? 0.3 : 1 }} ...>
```

Since the visible data might now be **stale** (last page's results, not this page's), `isPlaceholderData` is `true` for exactly that window — letting you visually signal "this is the old page, hang on" via the dimmed opacity, until the real data for the current page arrives and `isPlaceholderData` flips back to `false`.

### 3.3 `queryKey: ["products", page]` — Why `page` Is *Inside* the Key

This is the mechanism that makes per-page caching automatic: TanStack Query caches by key, so `["products", 0]` and `["products", 1]` are stored **separately**. Click `Prev` back to a page you've already visited, and — unlike `App.jsx` — it's served instantly from cache rather than refetched, *unless* it's gone stale by TanStack Query's own staleness rules.

### 3.4 `isPending` / `isError` — Handled Cases `App.jsx` Never Had

```jsx
if (isPending) return "Loading...";
if (isError) return "Something went wrong";
```

`useQuery` exposes these as **ready-made booleans** — no hand-rolled `isLoading` state to manage, and (unlike `App.jsx`, which has no error handling at all beyond a `console.log`) a failed request now has somewhere to actually show up in the UI.

## 4. `Infinite.jsx` — `useInfiniteQuery` for "Load More"

This solves a *different* shaped problem: not "replace page N with page N+1," but "keep everything loaded so far, and add more underneath it."

```jsx
let { data, isPending, fetchNextPage, hasNextPage, isFetchingNextPage } =
  useInfiniteQuery({
    queryKey: ["products"],
    queryFn: ({ pageParam }) => getAllProducts(limit, pageParam),
    initialPageParam: 0,
    getNextPageParam: (lastPage, allPage) => {
      let loadedData = allPage.length * limit;
      if (loadedData < lastPage.total) return loadedData;
      return undefined;
    },
  });
```

### 4.1 The Four Pieces That Make It Work

| Option | Job |
|---|---|
| `initialPageParam: 0` | What `pageParam` equals on the **very first** fetch |
| `queryFn: ({ pageParam }) => ...` | Receives whatever the *previous* `getNextPageParam` returned |
| `getNextPageParam(lastPage, allPages)` | Decides the **next** `pageParam` — or `undefined` to signal "no more pages" |
| `fetchNextPage()` | Called manually (here, from the "Load more" button) to trigger the next fetch |

### 4.2 Tracing `getNextPageParam`

```jsx
getNextPageParam: (lastPage, allPage) => {
  let loadedData = allPage.length * limit;
  if (loadedData < lastPage.total) return loadedData;
  return undefined;
},
```

- `allPage.length * limit` — how many products have been loaded **so far**, across every page fetched to date (3 pages × 40 = 120 loaded, say).
- If that's still less than `lastPage.total` (the API's reported total product count), there's more to fetch — return that count as the **next `skip` value**, which becomes next call's `pageParam`.
- Once `loadedData >= total`, returning `undefined` is what makes `hasNextPage` become `false` — this return value is the *entire* signal TanStack Query uses to know whether "Load more" should still be offered.
- Notice this reuses the same `getAllProducts(limit, pageParams)` from `productApi.jsx` as `TanStack.jsx` does — `pageParam` here plays exactly the role `page * limit` played manually in `App.jsx`; `useInfiniteQuery` just computes and threads that offset through for you instead of you tracking `page` in a `useState`.

### 4.3 `data.pages` — An Array of Pages, Not an Array of Products

```jsx
let allProducts = data?.pages?.flatMap((val) => val.products) ?? [];
```

- Unlike `useQuery`, where `data` is just *the* response, `useInfiniteQuery`'s `data.pages` is an **array of every page fetched so far** — `data.pages[0]` is page 1's whole response object (`{ products, total, skip, limit }`), `data.pages[1]` is page 2's, etc.
- `.flatMap((val) => val.products)` — pulls `.products` out of each page **and** flattens the resulting array of arrays into one flat list in a single step (`.map` alone would leave you with an array of arrays — one per page — that you'd then need a separate `.flat()` for).
- `?? []` — the nullish-coalescing fallback for the very first render, before `data` exists at all, so `.flatMap` is never called on `undefined`.

### 4.4 The Loading States, Split in Two

```jsx
if (isPending) return "loading...";
...
{hasNextPage && (
  <button onClick={() => fetchNextPage()}>
    {isFetchingNextPage ? "Loading.." : "Load more"}
  </button>
)}
```

`isPending` is the **first-ever** load (no data exists yet at all — worth a full-page loading state). `isFetchingNextPage` is specifically "a *later* page is loading, but everything fetched so far is still on screen" — that's why it only swaps the button's own label rather than blocking the whole grid the way `isPending` does. Two different moments in the same query's life, two different UI responses.

## 5. `productApi.jsx` — One Function, Two Callers

```jsx
export const getAllProducts = async (limit, pageParams) => {
  let res = await axios.get(`.../products?limit=${limit}&skip=${pageParams}`);
  return res.data;
};
```

The same function serves both `TanStack.jsx` (`getAllProducts(limit, page)` — an actual page number) and `Infinite.jsx` (`getAllProducts(limit, pageParam)` — a running `skip` offset). It doesn't care which meaning the second argument carries; it just plugs it into `skip=`. That's *why* it works for both: the difference between "page-based" and "cursor/offset-based" pagination lives entirely in how the **caller** computes that number, not in the fetch function itself.

## 6. Quick Summary

```
App.jsx (manual):
  useState + useEffect(..., [page])  → refetch on every page change
  no cache, no keepPreviousData      → visible flicker between pages

TanStack.jsx (useQuery, page-replace):
  queryKey: ["products", page]        → separate cache entry per page
  placeholderData: keepPreviousData   → old page stays visible while new one loads
  isPlaceholderData                   → true during that "still showing old page" window
  isPending / isError                 → ready-made states, no hand-rolled equivalents

Infinite.jsx (useInfiniteQuery, page-append):
  initialPageParam: 0                       → pageParam for the first fetch
  getNextPageParam(lastPage, allPages)      → returns next pageParam, or undefined = done
  fetchNextPage()                           → manually triggers the next page's fetch
  hasNextPage                               → driven entirely by getNextPageParam's return
  data.pages                                → array of raw page responses (not flattened)
  data.pages.flatMap(p => p.products)       → flatten into one product list to render
  isPending vs isFetchingNextPage           → "first load ever" vs "loading one more page"

productApi.jsx: one function (limit, offset) → offset means different things
  to different callers (page number vs running skip) — the function itself
  doesn't need to know or care which
```
