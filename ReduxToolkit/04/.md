# Real Auth with Thunks, Feature Folders & Debounced Search

## 1. What Changed Since `react-01`

This is the same app's **next iteration**, and the diff tells its own story:

| | react-01 | react-02 |
|---|---|---|
| **Folder shape** | Flat: `pages/`, `layout/`, `hooks/`, `features/` mixed loosely | **Feature-based**: `app/`, `features/auth/`, `features/products/`, `features/cart/`, `features/orders/`, `shared/`, `config/` |
| **Auth backend** | Fake — array in `localStorage`, plain-text password match | **Real** — `axios` calls to `/auth/login` and `/auth/me`, access token in `localStorage` |
| **Auth reducers** | Plain `reducers: { addUser, removeUser }` | **`extraReducers`** responding to async thunk lifecycle (`pending`/`fulfilled`/`rejected`) |
| **Guards** | Two states: logged in / not | **Three states**: loading / logged in / not — guards now wait for hydration before deciding |
| **Products** | Single `getProductsDataApi()` | Three separate endpoints — all products, categories, by-category — plus **debounced search** |

The throughline: this version replaces "pretend it's real" with actual async, server-backed state — which is exactly why a third state (`isLoading`) had to show up everywhere it didn't before.

## 2. Feature-Based Folder Architecture

Reading the import paths across these files sketches the structure even without seeing a file tree:

```
src/
  app/
    layout/        → AuthLayout, MainLayout (shared page shells)
    store.jsx       → Redux store
  config/
    api.jsx         → shared axios instance
  routes/
    AppRoutes.jsx
    protected/      → PublicProtected, MainProtected
  shared/
    ui/
      components/   → Navbar
      pages/        → HomePage, AboutPage
  features/
    auth/
      state/         → authSlice, authAction
      hooks/         → useAuthHook
      ui/pages/      → LoginPage, RegisterPage
    products/
      api/           → productApis
      hooks/         → useProductHooks
      ui/
        components/  → Filter, ProductCard
        pages/       → ProductPage
    cart/ui/pages/    → CartPage
    orders/ui/pages/  → OrderPage
```

**The organizing idea:** instead of grouping by *file type* (all pages together, all hooks together — react-01's shape), this groups by **feature** — everything auth-related lives under `features/auth/`, everything product-related under `features/products/`. `shared/` and `app/` hold what's genuinely cross-cutting (layouts, the Navbar, pages with no feature of their own like Home/About). This is why `Navbar.jsx` imports from `../../shared/ui/components/Navbar` rather than a flat `../components/` — the extra folder depth *is* the architecture.

## 3. Real Auth — `createAsyncThunk` + `extraReducers`

### 3.1 The Thunk Itself

```jsx
export const loginUserAction = createAsyncThunk(
  "auth/login",
  async (credentials, thunkApi) => {
    try {
      let res = await api.post("/auth/login", credentials);
      toast.success("user logged in");
      localStorage.setItem("accessToken", res.data.accessToken);
      return res.data;
    } catch (error) {
      toast.error("login failed");
      return thunkApi.rejectWithValue("login failed");
    }
  }
);
```

- `createAsyncThunk(typePrefix, payloadCreator)` wraps an async function so Redux Toolkit **automatically dispatches three actions** around it: `auth/login/pending` the instant it starts, then either `auth/login/fulfilled` (with your `return`ed value as the payload) or `auth/login/rejected` (if it throws) once it settles.
- `thunkApi.rejectWithValue(...)` is the "clean" way to fail — it still produces a `rejected` action, but with your custom payload (`"login failed"`) rather than a raw thrown error object.
- `hydrateUserAction` follows the identical shape, hitting `/auth/me` with the stored token as a `Bearer` header — this is what checks "is there already a valid session?" on app load, replacing react-01's `hydrateUser` that just read a user object back out of `localStorage` directly.

### 3.2 Catching the Three States — `extraReducers`

```jsx
extraReducers: (builder) => {
  builder
    .addCase(loginUserAction.pending, (state) => { state.isLoading = true; })
    .addCase(loginUserAction.fulfilled, (state, action) => {
      state.user = action.payload;
      state.isAuthenticated = true;
      state.isLoading = false;
    })
    .addCase(loginUserAction.rejected, (state) => { state.isLoading = false; })
    // ...same pattern repeated for hydrateUserAction
}
```

- `reducers` (the object literal, still visible here **commented out**) is for actions *you* define and dispatch directly (`addUser`, `removeUser` in react-01). `extraReducers` is for responding to actions defined **elsewhere** — here, the three auto-generated thunk lifecycle actions.
- `builder.addCase(actionCreator, reducerFn)` is just a type-safe way of saying "when this specific action fires, run this reducer" — six cases total (pending/fulfilled/rejected × two thunks), all following the same `isLoading` on/off rhythm.
- Notice `loginUserAction.rejected` and `hydrateUserAction.rejected` only reset `isLoading` — they don't clear `user` or `isAuthenticated`, since those were never set to begin with on a failed attempt. There's nothing here resetting them on **logout**, though — no `removeUser`-equivalent case exists yet in this version (the old commented-out reducer had one).

### 3.3 Why the Guards Now Have Three Branches

```jsx
// MainProtected.jsx
let { isAuthenticated, user, isLoading } = useSelector((store) => store.auth);
if (isLoading) return <h1>Loading state...</h1>;
if (!user) return <Navigate to={"/"} />;
return <Outlet />;
```

In react-01, `hydrateUser` was **synchronous** (`localStorage.getItem` returns instantly), so the guard only ever needed two branches: has a user, or doesn't. Now `hydrateUserAction` is a **real network request** — for the brief window between "app just mounted" and "the `/auth/me` call resolved," `user` is still `null` even for someone who's genuinely logged in. Without the `isLoading` check, `MainProtected` would incorrectly bounce a real logged-in user back to `/` for a split second on every refresh, before the hydration call finishes and the guard re-renders with the real answer. The loading branch exists purely to wait that window out.

## 4. Bugs Worth Flagging

A few things in this version are worth being aware of, since they'd surface as real issues once you click through the app rather than just read the code:

### 4.1 `LoginPage` — Field Name Mismatch

```jsx
<input {...register("username", { required: "username is required" })} ... />
{errors.email && <p className="text-red">{errors.email.message}</p>}
```

The field is registered as `"username"`, but the error check just below reads `errors.email` — copy-pasted from the old email-based version and not updated. As written, a missing username will **fail validation silently** (react-hook-form still blocks submit, but no message renders, since `errors.username` is what's actually populated). Also worth noting `loginForm` in `useAuthHook` sends whatever `data` react-hook-form collects straight to `loginUserAction(data)` — so the backend needs to expect a `username` field, not `email`, for this to actually authenticate correctly.

### 4.2 `useProductByCategory` — Fetches Before There's a Category

```jsx
const [category, setCategory] = useState(null);
let { data } = useQuery({
  queryKey: ["productsByCategory", category],
  queryFn: () => getProductByCategory(category),
});
```

`useQuery` runs its `queryFn` **as soon as the component mounts**, by default — there's no `enabled` option here to stop that. So on first render, before the user has picked anything from the `<select>`, this fires `getProductByCategory(null)` → a request to `/products/category/null`, a route that was never meant to be hit. The fix would be `enabled: !!category` in the query options, so the query only actually runs once a real category is chosen.

### 4.3 Mixed Auth Strategies in `config/api.jsx`

```jsx
export const api = axios.create({
  baseURL: "https://dummyjson.com",
  withCredentials: true,
});
```

`withCredentials: true` tells axios to send cookies with every request — the **cookie-based** session pattern. But `hydrateUserAction` separately reads a token out of `localStorage` and attaches it manually as `Authorization: Bearer ${token}` — the **token-based** pattern. Both can coexist, but doing both at once for the same login usually means one of them is leftover from an earlier approach rather than intentional; worth deciding on one and dropping the other once the backend's actual auth strategy is settled.

## 5. Products — Three Endpoints, One Debounce

### 5.1 The API Layer

```jsx
export const getAllPRoductApi = async (search) => {
  let url = search ? `/products/search?q=${search}` : "/products?limit=100";
  let res = await api.get(url);
  return res.data;
};
```

One function, **two different endpoints** depending on whether `search` has a value — searching hits `/products/search`, browsing everything hits `/products?limit=100`. `getProductsCategories` and `getProductByCategory` are the other two, each a thin wrapper around one `api.get(...)` call — this file's whole job is "know the URLs," nothing else.

### 5.2 Debouncing the Search Input

```jsx
const [search, setSearch] = useState(null);
const [debounceSearch, setDebounceSearch] = useState(null);

useEffect(() => {
  let timeout = setTimeout(() => {
    setDebounceSearch(search);
  }, 1000);
  return () => clearTimeout(timeout);
}, [search]);

let { data } = useQuery({
  queryKey: ["products", debounceSearch],
  queryFn: () => getAllPRoductApi(debounceSearch),
});
```

- Without this, every single keystroke in the search box would trigger a fresh API call — typing "shirt" would fire 5 requests, most of them immediately thrown away.
- The pattern: `search` updates instantly (so the input feels responsive), but `debounceSearch` — the value actually used in the query — only updates **1 second after the user stops typing**. Each keystroke resets the timer via the cleanup function (`return () => clearTimeout(timeout)`), which cancels the *previous* pending timeout before starting a new one — so only the final pause in typing actually results in an update.
- The query itself only re-runs when `debounceSearch` changes, since it's part of `queryKey: ["products", debounceSearch]` — react-query treats a different key as a different cache entry, refetching automatically.

### 5.3 `ProductPage` — Category Overrides Search

```jsx
{productByCategory?.products.length
  ? productByCategory?.products.map((product) => <ProductCard key={product.id} product={product} />)
  : data?.products.map((product) => <ProductCard key={product.id} product={product} />)}
```

The priority logic: **if a category is selected** (making `productByCategory.products` non-empty), show those results; **otherwise**, fall back to `data` — the general/searched product list. This does mean selecting a category and typing a search term at the same time won't combine them — category silently wins over search per this condition, which may or may not be the intended UX once both filters are meant to work together.

### 5.4 `Filter` — a Second, Independent Query

```jsx
const Filter = ({ search, setSearch, category, setCategory }) => {
  let { data, isPending, error } = useAllCategories();
  ...
  {data.map((item) => (
    <option key={item.slug} value={item.slug}>{item.name}</option>
  ))}
```

`useAllCategories()` is called **inside `Filter`**, separately from the product queries running in `ProductPage` — react-query's cache means this doesn't duplicate a network request if `Filter` and something else both asked for `["AllCategories"]`, but architecturally it's its own self-contained data need, not passed down as a prop the way `search`/`category` are.

## 6. Quick Summary

```
Folder shape:  feature-based — features/auth, features/products, features/cart,
               features/orders each own their state/hooks/ui; shared/ + app/ hold
               cross-cutting layout and pages with no single feature

createAsyncThunk(type, asyncFn)
  → auto-dispatches: pending → fulfilled (payload = return value) → rejected

extraReducers: builder.addCase(thunk.pending/fulfilled/rejected, reducerFn)
  → for reacting to actions NOT defined via this slice's own `reducers`

Guards now check THREE states, not two:
  isLoading → "waiting to know"     (new — hydration is now a real network call)
  !user     → "know: not logged in" → redirect
  else      → "know: logged in"     → <Outlet />

Bugs to watch for:
  - LoginPage: registers "username", checks errors.email  → mismatched validation display
  - useProductByCategory: no `enabled` guard → fires with category=null on mount
  - config/api.jsx: withCredentials (cookie) + manual Bearer token → two auth
    strategies active at once, likely leftover rather than intentional

Debounced search:
  raw `search` state updates instantly (responsive input)
  `debounceSearch` updates 1s after typing stops, via setTimeout + cleanup
  queryKey includes debounceSearch → query only refetches on the settled value

ProductPage render priority: productByCategory (if non-empty) WINS over
  the general/searched `data` — category and search don't currently combine
```
