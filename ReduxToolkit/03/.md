# Routing, Auth Guards, Redux & Data Fetching (Full App)

## 1. The Big Picture

This isn't a single concept anymore — it's a whole app wired together from five separate systems. Before the line-by-line, here's how the pieces connect:

```
main.jsx
  └─ QueryClientProvider   (react-query — server data caching)
       └─ Provider (redux)  (global client state — auth, counter)
            └─ AppRoutes    (react-router — decides WHICH page)
                 └─ PublicProtected / MainProtected   (guards — decides IF allowed)
                      └─ AuthLayout / MainLayout        (shared shell — Navbar, wrapper)
                           └─ actual page (Login/Register/Home/Shop/About)
```

Four different concerns, four different libraries, each nested inside the last: **caching → global state → navigation → access control → shared UI → page content.**

---

## 2. `main.jsx` — The Provider Stack

```jsx
createRoot(document.getElementById("root")).render(
  <QueryClientProvider client={queryClient}>
    <Provider store={store}>
      <AppRoutes />
      <ToastContainer />
    </Provider>
  </QueryClientProvider>
);
```

- **Order matters here.** `AppRoutes` needs Redux (it reads `store.auth` inside the guards), so `Provider` must wrap it. It doesn't strictly need `QueryClientProvider` to be *outside* Redux specifically — but react-query and redux are independent, so nesting either order inside the other works; this app just picks query-outside-redux.
- `<ToastContainer />` sits as a sibling to `AppRoutes`, not inside any particular page — this is the react-toastify pattern: mount the container **once** at the root, then any component anywhere can fire `toast.success(...)` / `toast.error(...)` and it renders here.
- Note: unlike the TS `main.tsx` from note 03, `getElementById("root")` here has **no `!`** — this is plain JS, so there's no type system to silence in the first place.

## 3. Routing — `AppRoutes.jsx`

### 3.1 Lazy Loading

```jsx
const AuthLayout = lazy(() => import("../layout/AuthLayout"));
const LoginPage = lazy(() => import("../pages/LoginPage"));
```

replacing the commented-out plain imports at the top. `React.lazy()` wraps a **dynamic `import()`** — instead of bundling every page into one giant JS file the browser downloads upfront, each page becomes its own chunk that only loads **when that route is actually visited**. First paint is faster; the trade-off is each lazy component needs a `<Suspense fallback={...}>` somewhere above it to show while its chunk downloads (worth adding around `<RouterProvider />` if it isn't elsewhere in the app already).

### 3.2 The Route Tree

```jsx
createBrowserRouter([
  {
    path: "/",
    element: <PublicProtected />,
    children: [
      { path: "", element: <AuthLayout />, children: [
        { path: "", element: <LoginPage /> },
        { path: "register", element: <RegisterPage /> },
      ]},
    ],
  },
  {
    path: "/main",
    element: <MainProtected />,
    children: [
      { path: "", element: <MainLayout />, children: [
        { path: "", element: <HomePage /> },
        { path: "shop", element: <ShopPage /> },
        { path: "about", element: <AboutPage /> },
      ]},
    ],
  },
]);
```

This is a **three-level nested tree**, and the nesting is the whole design:

```
/           → guard (PublicProtected) → shell (AuthLayout) → LoginPage
/register   → guard (PublicProtected) → shell (AuthLayout) → RegisterPage
/main       → guard (MainProtected)   → shell (MainLayout) → HomePage
/main/shop  → guard (MainProtected)   → shell (MainLayout) → ShopPage
/main/about → guard (MainProtected)   → shell (MainLayout) → AboutPage
```

Every route under `/` is gated by **one** guard component and wrapped in **one** shared layout — you write the guard/navbar once per section, not once per page.

### 3.3 `<Outlet />` — Where Children Actually Render

```jsx
// AuthLayout.jsx / MainLayout.jsx
<div>
  <Outlet />
</div>
```

`Outlet` is react-router's placeholder: "render whichever **child route** matched here." So visiting `/main/shop` renders `MainProtected` → which renders `MainLayout` → whose `<Outlet />` renders `ShopPage`. Each layer in the tree hands off to the next via its own `Outlet`, three levels deep.

### 3.4 Hydrating Auth on App Load

```jsx
const hydrateUser = () => {
  let loggedInUser = JSON.parse(localStorage.getItem("loggedInUser"));
  if (!loggedInUser) {
    toast.error("UnAuthorized user");
    return;
  }
  dispatch(addUser(loggedInUser));
};

useEffect(() => { hydrateUser(); }, []);
```

Redux state lives **only in memory** — a full page refresh wipes it clean. This app's workaround: keep a copy of the logged-in user in `localStorage` (a browser storage that *does* survive refresh), and on every app load, read it back out and re-populate Redux via `dispatch(addUser(...))`. This is why login "sticks" across refreshes even though Redux itself has no memory of it.

> Worth flagging: `toast.error("UnAuthorized user")` fires for **every visitor who simply isn't logged in yet** — including a first-time visitor who's never registered. That's a false "error" for the completely normal case of "nobody's logged in." Silently returning (no toast) when there's just no stored user, and reserving the toast for an actual failed auth attempt, would read more accurately.

## 4. Protected Routes — The Guard Pattern

```jsx
// PublicProtected.jsx — for routes that should only be visible when LOGGED OUT
const PublicProtected = () => {
  let { user } = useSelector((store) => store.auth);
  if (user) return <Navigate to={"/main"} />;
  return <Outlet />;
};

// MainProtected.jsx — for routes that should only be visible when LOGGED IN
const MainProtected = () => {
  let { user } = useSelector((store) => store.auth);
  if (!user) return <Navigate to={"/"} />;
  return <Outlet />;
};
```

Same shape, **inverted condition** — a clean mirror pair:

| | Guards | Redirects when | Redirects to |
|---|---|---|---|
| `PublicProtected` | Login/Register pages | user **IS** logged in (no point re-showing login) | `/main` |
| `MainProtected` | Home/Shop/About pages | user is **NOT** logged in (blocks the app) | `/` |

Both read `user` from Redux via `useSelector((store) => store.auth)`, and both fall through to `<Outlet />` (letting the nested route render) only when the condition passes. `<Navigate to={...} />` is react-router's **declarative** redirect — rendering it *is* the redirect, no imperative `navigate()` call needed inside a guard component.

## 5. State Management — Redux Toolkit

### 5.1 The Store

```jsx
export const store = configureStore({
  reducer: {
    counter: counterReducer,
    auth: authReducer,
  },
});
```

`configureStore` combines multiple **slices** into one global store. `store.auth` and `store.counter` in your `useSelector` calls map directly to these two keys.

### 5.2 A Slice — `authSlice.js`

```jsx
const authSlice = createSlice({
  name: "auth",
  initialState: { user: null, isAuthenticated: false },
  reducers: {
    addUser: (state, action) => {
      state.user = action.payload;
      state.isAuthenticated = true;
    },
    removeUser: (state) => {
      state.user = null;
      state.isAuthenticated = false;
    },
  },
});
```

- `createSlice` bundles **state shape + the reducers that change it + auto-generated action creators** in one call — `addUser`/`removeUser` become both the reducer functions here *and* the action creators exported below (`authSlice.actions`).
- `state.user = action.payload` — this looks like direct mutation, which is normally forbidden in Redux. Under the hood, Redux Toolkit wraps every reducer in **Immer**, which lets you *write* mutation-style code while it actually produces a new immutable state object — safe here specifically because it's inside a `createSlice` reducer.
- `counterSlice.js` follows the identical shape — `increment`/`decrement`/`incrementByValue` each also mutate `state.count` directly, same Immer safety net.

### 5.3 Reading & Writing From Components

```jsx
let { user } = useSelector((store) => store.auth);   // READ
dispatch(addUser(loggedInUser));                       // WRITE
```

`useSelector` subscribes the component to a slice of the store (re-renders when `store.auth` changes); `dispatch` sends an action through the reducer to update it. This read/write pair is the entire Redux vocabulary you need for both slices in this app.

## 6. Forms — `useAuth` Hook (react-hook-form)

```jsx
let { register, handleSubmit, reset, formState: { errors } } = useForm();
```

- `register("email", { required: "email is required" })` — spread onto an `<input>` via `{...register(...)}`, this wires the input into react-hook-form's internal tracking **without** you writing `useState` + `onChange` by hand for every field, and attaches the validation rule (`required`, `minLength`, etc.) at the same time.
- `errors.email.message` — when validation fails, react-hook-form populates `errors` with exactly the message string you defined in `register(...)`, ready to render straight under the field.
- `handleSubmit(loginForm)` — wraps your own `loginForm` function so it **only actually runs if every field passes validation first**; `handleSubmit` intercepts the raw submit event, runs validation, and only then calls your function with the clean `data` object.

### The Fake-Backend Pattern

```jsx
const registerForm = (data) => {
  let arr = [...registeredUsers, data];
  setRegisteredUsers(arr);
  localStorage.setItem("registeredUsers", JSON.stringify(arr));
};

const loginForm = (data) => {
  let user = registeredUsers.find(
    (val) => val.email === data.email && val.password === data.password
  );
  if (!user) { toast.error("invalid something.."); return; }
  dispatch(addUser(user));
  localStorage.setItem("loggedInUser", JSON.stringify(user));
};
```

There's no real backend here — registration just **appends to an array stored in `localStorage`**, and login **searches that same array** for a matching email+password. It's a genuinely useful pattern for prototyping an app's flow before a real auth API exists, but worth being explicit with yourself that it's a stand-in: passwords are stored and compared in **plain text**, visible to anyone opening devtools → Application → Local Storage.

## 7. Data Fetching — Two Competing Patterns Side by Side

This app actually has **two different hooks** solving the same problem (`useProductApi` and `useProduct`), which is worth noticing explicitly since only one (`useProduct`) is the one `ShopPage` actually imports and uses.

| | `useProductApi` (unused in ShopPage) | `useProduct` (actually used) |
|---|---|---|
| **Fetch mechanism** | `useQuery` from **react-query** | Manual `useEffect` + `async` function |
| **Loading state** | `isPending` (react-query gives you this for free) | Hand-rolled `isLoading` state, manually set `true`→`false` |
| **Caching** | Automatic — react-query caches by `queryKey: ["products"]" | None — refetches from scratch every mount |
| **Error handling** | `error` object from react-query | None visible — a failed fetch would leave `isLoading` stuck `true` forever |

```jsx
// useProductApi — react-query version
let { isPending, data, error } = useQuery({
  queryKey: ["products"],
  queryFn: getProductsDataApi,
});
```
```jsx
// useProduct — manual version, what ShopPage actually calls
let getProducts = async () => {
  let data = await getProductsDataApi();
  setProductsData(data);
  setFilteredProducts(data);
  setIsLoading(false);
};
useEffect(() => { getProducts(); }, []);
```

This is a natural stage in learning data-fetching: write it manually first (full control, more boilerplate, you handle every state yourself), then reach for a library like react-query once you feel the repetition — `QueryClientProvider` is already wired up in `main.jsx`, so `useProductApi` is one hook away from being the one actually used, once `filterProducts` inside it is finished (right now it filters `data` directly with no null-check, which will throw if `filterProducts` runs before the query resolves).

### 7.1 `axiosInstance` — Not Repeating the Base URL

```jsx
export const axiosInstance = axios.create({
  baseURL: "https://dummyjson.com",
});
```

vs. note 03's raw `axios.get("https://fakestoreapi.com/products")`. `axios.create()` produces a **pre-configured** axios — every call through `axiosInstance.get("/products")` automatically prefixes the `baseURL`, so as the app grows past one endpoint you write `/products`, `/users`, `/cart` instead of the full URL each time.

## 8. UI Details Worth Naming

### 8.1 Skeleton Loading — `ProductCardSkeleton`

```jsx
{isLoading
  ? Array.from({ length: 8 }).map((_, index) => (
      <ProductCardSkeleton key={index} />
    ))
  : filteredProducts?.map((product) => <ProductCard key={product.id} product={product} />)}
```

- `Array.from({ length: 8 })` — a common trick to generate a "loop 8 times" array with no real data, purely to render 8 placeholder cards while the real data is loading. `key={index}` is acceptable here specifically *because* skeletons have no identity or reordering of their own — the general "avoid index as key" advice is about lists that can reorder/filter, which doesn't apply to a fixed placeholder grid.
- `filteredProducts?.map(...)` — the `?.` (optional chaining) guards against `filteredProducts` being `null`/`undefined` on the very first render before data arrives, returning `undefined` (renders nothing) instead of throwing.
- The skeleton's markup (`h-60`, `h-6 w-3/4`, `h-8 w-24`, etc.) deliberately mirrors the real `ProductCard`'s layout dimensions — that's what makes the loading state feel like a preview of the real card rather than a generic spinner.

### 8.2 `NavLink`'s Active-State Callback

```jsx
<NavLink
  className={({ isActive }) => (isActive ? "text-yellow-500" : "")}
  to={"/main"}
  end
>
```

Unlike a plain `Link`, `NavLink` accepts a **function** for `className` (or `style`), called with `{ isActive }` so you can style the currently-active link differently — here, yellow text when it's the current route. `end` on the `/main` link specifically means "only match `/main` exactly," so the Home link doesn't stay lit up while you're actually on `/main/shop`.

### 8.3 Local Quantity State in `ProductCard`

```jsx
const [quantity, setQuantity] = useState(1);
onClick={() => quantity > 1 && setQuantity(quantity - 1)}
```

Quantity lives **inside** `ProductCard` itself, not lifted up to `ShopPage` or Redux — each card manages its own counter independently, which makes sense since no other part of the app needs to know a card's quantity *until* "Add to Cart" is actually clicked (which isn't wired up yet). `quantity > 1 && setQuantity(...)` is a short-circuit guard preventing the count from ever going below 1, without a separate `if`.

## 9. Quick Summary

```
Provider nesting (main.jsx):
  QueryClientProvider → Provider(redux) → AppRoutes → ToastContainer

Routing (AppRoutes.jsx):
  createBrowserRouter + nested `children` = guard → layout → page, 3 levels deep
  <Outlet /> = "render whichever child route matched" — one per layout
  lazy(() => import(...)) = code-split each page into its own chunk

Guards (PublicProtected / MainProtected):
  useSelector(store => store.auth) → read user
  <Navigate to="..." />             → declarative redirect
  mirror pair: one blocks logged-IN users, one blocks logged-OUT users

Redux (store.js / *Slice.js):
  configureStore({ reducer: { auth, counter } })
  createSlice → state + reducers + action creators, one call
  reducers "mutate" state directly — safe only because Immer intercepts it

Forms (useAuth.js):
  useForm() → register() wires inputs, handleSubmit() validates-then-calls,
  errors.field.message → validation feedback
  fake backend: users array stored in localStorage — fine for prototyping,
  not real auth (plaintext passwords, no real security)

Data fetching (productHooks.js):
  two patterns side by side — manual useEffect+useState (used) vs.
  react-query's useQuery (wired up, not yet used) — same job, react-query
  adds caching + isPending/error for free

UI:
  Array.from({length:n}) → skeleton placeholders while isLoading
  data?.map(...)          → optional chaining guards against not-yet-loaded data
  NavLink className={({isActive}) => ...} → style the current route differently
```
